# 舊系統資料剖析 — legacy_profile.md

資料來源：`legacy_csv/業績資料表.csv`（8,547 列）與其他主檔。此文件的目的是讓 ETL 與報表驗證有客觀對照值。

## 關鍵發現（ETL 設計依據）

1. **資料粒度是「線（line）」不是「合約」**：`業績資料表` 一列 = 一個合約編號 × 一個電台/平台/製作費項目 × 一個節目，平均每個合約 3.9 列（最多 48 列）。合約編號共 2,216 個、客戶 511 個、業務 35 人。
2. **同一合約編號內，客戶名稱/組別/業務可能不同**（639 / 693 / 107 個合約），原因是：(a) 子公司對聲活的內部轉撥線（組別 = `聲活-東`、`聲活-鉑`，客戶 = `東吳廣告` 等）與客戶線放在同一合約編號下；(b) 同一客戶用不同名稱登打（如「家樂福電信股份有限公司」vs「家福股份有限公司」）。→ 新系統的 line 必須自己帶客戶/業務/組別，不可只放在 header。
3. **製作費是線**：`電台` 以 `製作費-` 開頭的列（製作費-錄音室 1,899 列、製作費-配音員 1,654 列、製作費 119 列）代表成本線，1,381 個合約同時有媒體線與製作費線。
4. **雙層毛利已存在於資料中**：例如合約 1130825-6-6，東吳對客戶線 實收 380,952 / 實付 247,619；聲活-東線 實收 247,618 / 實付 0。247,619 ≈ 380,952 × 0.65，即 PDF 所說的 65 折。第一層毛利 = 子公司線的（除佣實收 − 實付）；第二層 = 聲活（含聲活-東/聲活-鉑線）的（除佣實收 − 實付 − 該月平台固定成本）。
5. **公司別有 4+2 個**：聲活 3,044 列、東吳 2,252、瑞迪 2,216、鉑霖 1,033、錄音室 2；`公司資料表` 另有 `聲活-東`、`聲活-鉑`。PDF 只提到聲活/東吳/鉑霖，**瑞迪（RD）漏掉了**。
6. **廣播業務仍在**：平台 = 廣播 3,233 列，電台 92 種（BEST989、港都、山海屯、亞洲…）。PDF 沒提到電台，但不能拿掉。
7. **平台清單（`平台資料表`，12 筆）**：廣播、新鮮視、全家企頻、家樂福企頻、健康視、其它、全家全企、全家北企、全家桃企、全家中企、全家南企、營運；`平台歸類` = 廣播/新鮮視/企頻/診所/其它/分區/營運。PDF 的「區域」在舊系統是用「全家北企/中企/南企/桃企」這種平台名稱表達的。實際資料還出現 `企頻`、`企頻-年度維運費`、`Podcast`（不在主檔內，ETL 需自動補建）。
8. **業績年月份範圍 2024/01 → 2027/06**（2024：2,200 列、2025：3,933、2026：2,378、2027：24），格式 `YYYY/MM` 文字。`合約期限`、`新案千大` 兩欄全空。
9. **退佣折扣** 存的是百分比數字（0、10、15、20、21.6、22.24、70…），`除佣實收 = 實收金額 × (1 − 退佣折扣/100)`（請以資料驗證，允許四捨五入差 1 元）。
10. **發票開立資料表** 3,237 筆：收款方式 匯款 2,144 / 支票 1,069 / 收現 24；折扣方式幾乎全是「先現折 再退」；有銷帳日的只有 176 筆、`銷帳日期-業助` 65 筆、`銷帳日期-財務` 0 筆 → 舊系統的銷帳功能幾乎沒被使用，新系統的銷帳模組可以重新設計，不必相容。
11. **獎金百分比資料表** 925 筆：維度 = 業務 × 平台（企頻/數位/廣播/單元/VERSE/Podcast/新鮮視/全家南企…）× 業績項目（服務/開發/直客/4A）× 年月區間，欄位含 獎金百分比、業績門檻、數位毛利低標/高標、企頻加碼、企頻團隊。MVP 只實作「業務 × 平台歸類 × 業績項目 × 區間 → 獎金%、門檻」一層。
12. **業績類別資料表** 有 `毛利認定比例`（開發* = 1.0、既有* = 0.8、服務*/4A = 0.5）與上層 `類別`（開發/既有/服務/4A）→ 這就是「業績認定表」的核心規則。
13. **修改歷史記錄資料表** 10,134 筆 = 舊系統的 audit log（整列複製）。匯入為 legacy 參考即可。
14. **PASSWORD 表** 225 列 = 31 個使用者 × 選單權限（MARK = 選單編號、主選單 = 1/2/3/5）。密碼為明文，**不得**搬到新系統；`legacy_users.csv` 只保留使用者名稱與機密報表權限旗標。

## 公式驗證

- `除佣實收 ≈ 實收金額 × (1 − 退佣折扣/100)` 在 99.7% 的列成立（誤差 ≤ 1 元）。不成立的列多為手動調整，ETL 一律以資料庫中的 `除佣實收` 原值為準，不重算。
